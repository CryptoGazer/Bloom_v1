## Основные находки

### P1. Поворот на перекрёстке может исчезнуть или появиться слишком поздно

**Где:** `web/m/m.js:1253`, `:1263` в `c152d59` (`buildPath`).

**Воспроизведение:** две соединённые улицы с разными названиями, каждая задана двумя координатами; на стыке поворот 90° налево. Функция возвращает только инструкцию прибытия. Общая точка перекрёстка отбрасывается до смены идентификатора сегмента; следующая точка уже находится после перекрёстка и может оказаться концом маршрута.

**Результат для пользователя:** навигатор пропустит поворот или даст неверную/позднюю команду. Вычислять манёвр в общей точке двух рёбер с входящим и исходящим направлением. Отдельно учитывать повороты на улицах, где название не меняется.

**Доказательство:** `missing-junction-turn` в локальном Node-воспроизведении.

### P1. Навигатор объявляет прибытие в километре от назначения

**Где:** `web/m/m.js:1332–1345`, функции `project` и `onPos`.

**Воспроизведение:** передать точную GPS-позицию в 1105 м за концом маршрута. Ближайшая проекция попадает в конец пути; остаток равен нулю. Код показывает «Вы на месте», останавливает навигацию и возвращается к результатам.

**Причина:** прибытие зависит только от расстояния вдоль проекции; расстояние от фактической позиции до маршрута/назначения и точность GPS не проверяются. Ветка прибытия выполняется раньше предупреждения о сходе с маршрута.

**Исправление:** проверять близость к конечной точке с учётом точности GPS, не продвигать прогресс по далёкой проекции. Проверить также откаты GPS: текущий `Math.max` необратимо сохраняет ошибочный скачок вперёд.

**Доказательство:** `false-arrival-far-off-route`.

### P1. Одна ошибка GPS автоматически заменяет реальное движение симуляцией

**Где:** `web/m/m.js:1296`, `:1301–1313`.

**Воспроизведение:** запустить обычную навигацию без `?sim=1`; GPS-watch сообщает единственный timeout. Код удаляет watch и запускает движение по маршруту в шесть раз быстрее. За первый тик 0,5 с в воспроизведении позиция продвинулась на 4,05 м.

Пометка «СИМУЛЯЦИЯ» есть, но реальный GPS уже не восстановится в этой сессии навигации. Потребуется новый запуск.

**Исправление:** при ошибке сохранять маршрут и показывать состояние ожидания GPS/повтор; демонстрацию запускать явным действием пользователя или параметром демо.

**Доказательство:** `gps-error-starts-fake-movement`.

### P1. Нулевой маршрут ломает навигацию

**Где:** `web/m/m.js:1310`, `:1333`, `:1369`.

**Шаги:** выбрать одинаковые A и B (`45.749852,21.240281`) в пешем режиме и нажать запуск навигации. Настоящий HTTP-ответ содержит 0 м / 0 минут, один feature и две одинаковые координаты. `buildPath` удаляет повтор и оставляет одну точку. После первого GPS-обновления `project` возвращает `null`, а `onPos` обращается к `pr.d`. В режиме демонстрации первый тик обращается к отсутствующей `P[1]`. В Node оба пути подтверждены TypeError; пустая геометрия также ломает начальную отрисовку.

**Исправление:** для нулевого/почти нулевого пути показывать «Вы уже на месте» до запуска навигатора; защищать функции проекции и симуляции от менее чем двух различных точек.

**Доказательство:** настоящий `../output/qa-zero-route.json` и `zero-length-navigation-crashes` в Node-воспроизведении.

### P2. Enter выбирает адрес от предыдущего поискового запроса

**Где:** `web/m/m.js:400–404`, `:447–455`.

**Шаги:** дождаться подсказок для одного адреса → заменить текст другим → нажать Enter до нового ответа. `sItems` остаётся от прежнего запроса во время debounce и загрузки; обработчик выбирает старую строку. При ошибке сети прежние варианты тоже остаются.

**Исправление:** сразу инвалидировать подсказки при вводе, привязать их к тексту и полю; не разрешать выбор устаревшего списка. Добавить состояния загрузки и ошибки.

**Доказательство:** `enter-chooses-stale-search-result` — введено `New destination`, выбрано `Previous destination`.

### P2. Завершившийся расчёт отменяет действие «Назад»

**Где:** `web/m/m.js:299`, `:491–499`.

**Шаги:** начать расчёт → вернуться домой/к поиску → приходит задержанный ответ. Экран снова переключается на старые результаты. В воспроизведении переходы: `results → home → results`.

**Причина:** уход с экрана не инвалидирует `routeReq`; ответ меняет экран без проверки актуальности намерения пользователя.

**Исправление:** при отмене или смене сценария отменять запрос либо увеличивать поколение расчёта; устаревший ответ не должен менять экран или показывать ошибку нового сценария.

**Доказательство:** `pending-route-overrides-back-navigation`.

### P2. «18 min» для транспорта исключает ещё пять минут до выхода

**Где:** `web/m/m.js:1027`, `:1037`; `backend/transit.py:201–205`.

**Реальный запрос:** A `45.7470,21.2395`, B `45.7548,21.2254`, `mode=transit`, `at=2026-11-15T21:00`.

API возвращает выход около `21:05`, прибытие `21:23`, длительность поездки около 18 минут и отдельный `wait_min`. В карточке крупно показано `18 min`; ожидание до выхода не подписано рядом. Пешком — 20,7 минуты с исходных 21:00, то есть прибытие раньше транспорта. В `c152d59` убрано и пояснение о сравнении с пешим вариантом. Возможность переключиться на пеший режим осталась.

**Предложение:** явно показывать «23 мин от выбранного времени · выйти в 21:05», отдельно «18 мин в пути». Сравнивать варианты на общей временной основе. Решение предлагать меньше времени пешком на улице можно сохранить, назвав эту выгоду прямо.

### P2. При A = B транспорт предлагает 19 минут возвращаться в исходную точку

**Запрос:**

```text
/api/route?from=45.749852,21.240281&to=45.749852,21.240281&mode=transit&at=2026-11-15T21:00
```

**Результат:** 19,4 минуты: пешком 579 м → троллейбус 16 → пешком 667 м. Пешие альтернативы правильно равны 0 м / 0 минут. Нужен порог «уже на месте» перед предложением поездки и запуском навигации.

### P2. Время с часовым поясом ломает все три режима маршрута

**Где:** `backend/app.py:69`, `:224`, `backend/liveliness.py:72`.

**Реальный запрос:** те же A/B, `at=2026-11-15T21:00:00%2B02:00` либо `2026-11-15T19:00:00Z`. HTTP 500 для walk, bike и transit; без суффикса зоны — 200.

`fromisoformat` принимает значение с зоной, но библиотека opening_hours затем получает неподходящий timezone и падает с `'datetime.timezone' object has no attribute 'key'`. Нормализовать время в Europe/Bucharest либо отвергать неподдержанный формат контролируемым 422. Это API-граничный случай; барабаны времени сами такой формат не создают.

### P2. Конец загруженного расписания выдаётся за отсутствие транспорта

**Где:** `backend/transit.py:77`, `:179`.

Сборка содержит только 14–16 ноября. Запрос того же пути на `2026-11-17T21:00` возвращает `reason=no_trip_soon`, `last=null`, `next=null`. На самом деле у сервера просто нет расписания этой даты.

Нужны отдельное состояние «расписание на эту дату не загружено» и регулярное обновление диапазона. Для текущего дня 15 ноября данные есть.

## Дополнительные замечания

- **P2, клавиатурная доступность:** окно времени объявлено `aria-modal=true` (`web/m/m.js:1427`), но не содержит удержания фокуса и не делает фон `inert`. Обработка Escape идёт через общий `closeOverlays`, минуя возврат фокуса `closeTimePicker`. Вывод по коду; реальная клавиатурная проверка не выполнена.
- **P2 для Windows-разработки:** полный `pytest backend/tests -q` останавливается при сборе `backend/tests/test_transit_logger.py`: импорт `fcntl` в `scripts/transit/logger.py:20`. Сам логгер тоже не запускается на Windows. Остальные 141 тест прошли.
- **P3:** `/api/segments?bbox=21,nan,22,46` возвращает 500 вместо 422: проверка bbox не отвергает NaN.
- **P2/P3, API:** `backend/live.py:173–175` при прямом совпадении `trip_id` не проверяет день экземпляра рейса. В синтетической проверке рейс прошлого дня с повторяющимся ID сегодняшней машины получает `status=live` и отрицательный ETA порядка суток. Ограничить live-сопоставление соответствующим днём/окном отправления. Это проверка API, не воспроизведение обычного UI-потока.
